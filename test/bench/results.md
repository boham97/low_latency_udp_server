# slot_vs_index — 큐에 데이터를 직접 vs 인덱스를 싣기

환경: WSL2 + Docker, 12코어. 절대 수치 무의미, 변형 간 상대 비교만.

`include/ll/spsc_queue_cached.h` 하나로 네 변형을 만든다. 큐 용량 1024,
producer(코어 0) / consumer(코어 1) 고정, items = 2,000,000.

| 변형 | 큐가 담는 것 | 데이터 위치 |
|---|---|---|
| `copy` | 데이터 | 링 슬롯 — `push(q,&item)`이 `buf[tail] = *item` |
| `borrow` | 데이터 | 링 슬롯 — `push_begin`으로 받은 주소에 직접 씀 |
| `index` | `uint32_t` 인덱스 | 별도 풀 (크기 = 큐 용량, 순차 접근) |
| `scatter` | `uint32_t` 인덱스 | 별도 풀 (8배 크기, stride 5로 흩어짐) |

**공정성**: 네 변형 모두 같은 양의 유효 데이터만 쓴다 (ts / seq / pad 첫·끝
바이트). 차이로 남는 것은 큐가 강제하는 복사와 메모리 접근 패턴뿐 —
`copy`는 유효 데이터가 16B여도 `sizeof(TYPE)` 전체를 옮긴다.

각 조합을 별도 프로세스로 **9회** 실행 (한 프로세스에서 연달아 돌리면 앞 실행이
캐시/TLB를 예열한다). 회차마다 변형 순서를 섞어 드리프트가 특정 변형에 몰리지
않게 했다. 아래는 9회 중앙값(범위).

## throughput (M msg/s) — 주 지표

| payload | copy | borrow | index | scatter |
|---|---|---|---|---|
| 16B | **48.5** (48.0–50.0) | **49.5** (45.2–50.7) | **36.7** (35.4–43.2) | **43.0** (41.3–45.8) |
| 64B | **48.4** (43.4–55.9) | **52.2** (51.2–57.2) | **45.7** (43.7–48.1) | **42.2** (40.5–45.5) |
| 2048B | **16.1** (14.3–16.7) | **59.5** (57.4–60.6) | **41.8** (38.9–45.7) | **32.7** (32.0–34.3) |

## push→pop p50 (TSC 사이클) — 참고

cap=1024는 큐잉 대기시간이 지배해 핸드오프 비용 지표로 부적합하다
(`bench/results.md`의 큐 깊이 노트). throughput과 역상관인지 확인용으로만 본다.

| payload | copy | borrow | index | scatter |
|---|---|---|---|---|
| 16B | 71,155 | 70,839 | 96,390 | 83,441 |
| 64B | 72,905 | 66,273 | 79,135 | 80,745 |
| 2048B | 215,040 | 57,995 | 84,630 | 90,265 |

## 결론

### 1. 인덱스 전달은 모든 크기에서 진다 (borrow 대비 -12% ~ -30%)

| payload | borrow → index |
|---|---|
| 16B | 49.5 → 36.7 (**-26%**) |
| 64B | 52.2 → 45.7 (-12%) |
| 2048B | 59.5 → 41.8 (**-30%**) |

세 크기 모두 9회 범위가 겹치지 않는다 — 각 크기에서 borrow의 최저값이 index의
최고값보다 크다 (16B 45.2 > 43.2, 64B 51.2 > 48.1, 2048B 57.4 > 45.7).

**캐시라인 스트림이 1개에서 2개로 늘기 때문.** borrow는 producer가 쓴 링
슬롯을 consumer가 그대로 읽어 코어 간에 오가는 라인이 데이터 하나뿐이다.
index는 인덱스 큐 라인 하나 + 풀 라인 하나가 각각 producer→consumer로
넘어가고, consumer는 인덱스를 읽고 나서야 풀 주소를 알기에 **로드 의존성**까지
생긴다. CLAUDE.md의 "큐에 포인터나 인덱스를 싣지 않는다"는 이 수치로 뒷받침된다.

### 2. 복사는 2KB부터 아프다 (그전엔 노이즈)

- 16B / 64B: copy와 borrow가 사실상 동일 (48.5 vs 49.5, 48.4 vs 52.2 —
  9회 범위가 넉넉히 겹친다). **한 캐시라인 안에서 끝나는 복사는 공짜에 가깝다.**
- 2048B: 16.1 vs 59.5 — **borrow가 3.7배.** 값 복사 API는 producer 스택→링,
  링→consumer 스택으로 **2KB를 두 번** 옮긴다. p50도 215k vs 58k 사이클.

즉 슬롯 대여 API의 복사 제거 효과만 놓고 보면 작은 페이로드에선 의미가 없고,
데이터그램 크기(2KB)에서 결정적이다. 지금 파이프라인의 `rx_msg_t`는 64B이므로
**복사 제거보다 아래 3번이 실질적인 이유다.**

### 3. 예상 밖: borrow는 페이로드가 클수록 빨랐다 (49.5 → 52.2 → 59.5)

복사량이 128배 늘었는데 throughput이 올랐다. 원소가 작으면 **링에서 한 캐시라인을
여러 원소가 공유**해서다 — 16B면 라인 하나에 4개, producer가 슬롯 i를 쓰는 동안
consumer는 같은 라인의 슬롯 i-3을 읽어 라인이 핑퐁한다. 2KB면 슬롯 하나가
라인 32개라 겹칠 일이 없다.

`index`가 16B에서 `scatter`보다 **느린** 것도 같은 이유다 (36.7 vs 43.0).
scatter는 stride 5 × 16B = 80B 간격이라 연속 원소가 다른 라인에 떨어져 오히려
핑퐁이 줄었다. 흩어진 접근이 이겼다기보다 **인접 접근이 졌다.**

→ 이래서 `rx_msg_t`를 64B(캐시라인 1개)에 맞춘 것이 맞다. 원소가 라인보다 작으면
링 자체가 false sharing 면이 된다.

### 4. 풀이 커지면 인덱스 방식은 더 나빠진다

2048B에서 index 41.8 → scatter 32.7 (-22%). 풀 8배(2MB→16MB) + 비순차 접근으로
프리페처가 무력해지고 TLB 미스가 늘었다. 반환이 FIFO가 아닌 실제 mempool은
scatter 쪽에 가깝다 — CLAUDE.md가 "mempool은 파이프라인에 쓰지 않는다"고 한 것과
같은 방향.

## 한계

- cap=1024만 측정했다. 얕은 큐(cap=8, lockstep)에서 핸드오프 비용만 분리한 값은
  없다 — `bench/results.md`의 방법론대로면 그쪽도 재야 완결이다.
- 3회 실행 때 `borrow` 64B가 1회 37.0으로 튀었으나 9회에선 재현되지 않았다
  (51.2–57.2). WSL2 단발 노이즈로 결론. 남은 최대 변동은 `copy` 64B의 26%
  (43.4–55.9)인데, 이 조합은 애초에 결론에 안 쓰인다(2번의 "겹친다").
- 사이클→ns 변환은 하지 않았다 (하이퍼바이저 환경에서 TSC 주파수 신뢰 불가).
